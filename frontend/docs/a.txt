
AUSTRALFINANCE — IMPLEMENTACIÓN FASE 2 DATA LAYER DEL FRONTEND

OBJETIVO

Implementar la Fase 2 del frontend de AustralFinance.

El objetivo es conectar el frontend actual con el backend real mediante una Data Layer limpia, desacoplada y mantenible.

IMPORTANTE:

El frontend que estás viendo actualmente es la versión LOCAL del frontend.

El repositorio contiene además el backend y blockchain en carpetas separadas dentro del mismo proyecto.

No asumas que el contrato del backend que aparece en documentación anterior coincide exactamente con el backend actual.

ANTES DE IMPLEMENTAR LA FASE 2 DEBES REVISAR EL BACKEND LOCAL.

La estructura general del proyecto es similar a:

AustralFinance/
├── frontend/
├── backend/
└── blockchain/

El backend local debe ser utilizado como fuente de verdad para verificar:

- endpoints reales
- métodos HTTP
- payloads reales
- nombres de campos
- estructura de objetos
- timestamps
- unidades
- estados
- Oracle

No inventes contratos basándote únicamente en este documento.

2. PRIMER PASO OBLIGATORIO: REVISAR EL BACKEND
--------------------------------------------------

Antes de modificar el frontend:

1. Ubica la carpeta backend dentro del proyecto.
2. Inspecciona su estructura.
3. Identifica cómo se levantan los endpoints.
4. Busca las rutas reales.
5. Revisa los schemas, tipos, controllers, services o handlers correspondientes.
6. Determina los payloads reales de:

GET /health
GET /oracle/price/YPF
GET /market/YPF-PERP

7. Verifica si las rutas anteriores realmente existen con esos nombres.
8. Si las rutas tienen diferencias respecto de esta especificación, utiliza el contrato REAL del backend.
9. Verifica los nombres y tipos reales de los campos.
10. Verifica las unidades.
11. Verifica timestamps.
12. Verifica el Circuit Breaker.
13. Verifica CCL.
14. Verifica HIP-3.
15. Verifica Pusher.
16. Verifica qué información realmente está disponible.

IMPORTANTE:

No modificar el backend para hacer que coincida con el frontend.

El backend es la fuente de verdad.

Si el frontend espera un campo que el backend no entrega, adaptar el frontend mediante normalización y dejar el campo como unavailable cuando corresponda.

No crear campos falsos en el backend.

No modificar contratos del backend como solución rápida.
